# Samir Liaquat · Ecommerce Growth Sprint

Vercel redesign of saamir140/saamir. The v3 owner-input addendum takes precedence on the homepage hierarchy, six-step method, four sprint phases, audience and brand voice. The approved production release is a separate step. The review build uses Samir, the spelling in the brief, and an illustrative notebook in place of a personal portrait. Research links and observations are in [the competitor review](docs/research.md).

## Run and deploy

Use Node 22 or newer. No runtime packages or API credentials are needed to inspect the pages. Run `npm run dev` for a local preview or `npm run build` to generate dist. Run `npm test` for lead handler regression checks. The Vercel project should use the repository root, Other framework preset, the build command and dist output in vercel.json. Use Vercel Preview for owner review. The public index is controlled by PUBLIC_LAUNCH=approved at build time. Review builds discourage indexing. This is independent of INTAKE_ENABLED.

Routes are /, /about, /process, /case-studies, /apply, /thank-you, /privacy, /terms and /404. Vercel serves 404.html for missing pages. The content build, field definitions, cases and styles are in scripts/build.js, lib/fields.js, src/content.js and public/style.css. Only dist and api are served. The thank-you page displays a receipt after server acknowledgment. Unknown/direct visits show a neutral application status.

## Owner-controlled intake

1. Create a restricted Supabase project in the chosen region. Apply db/schema.sql as project administrator. Records live under growth_private. Anonymous and signed-in site visitors cannot access the records or execute the two service RPCs. Give the reviewer least-privilege dashboard access. Do not enable public table access.
2. Verify a sending domain in Resend. Set EMAIL_FROM and a monitored REVIEW_EMAIL for replies. Store real credentials only in Vercel server environment settings. See .env.example. Generate a random RATE_SECRET. Set SITE_ORIGIN to the actual origin without a trailing slash. Configure Preview and Production independently.
3. For staging, use test data and controlled recipient inboxes. Enable INTAKE_ENABLED=true and rebuild. Submit from /apply. Check the stored UUID, consent timestamp, payload and both emails. Verify a repeated request with the same key returns the original record. Confirm the acknowledgment was delivered by inspecting both mailboxes, including spam. A provider acceptance alone does not establish inbox delivery.
4. After owner approval of identity, commercial terms, portrait or alternative, vendors, notices, retention, domain and recipient, release through the existing Vercel project. Approve proof independently. Keep unreleased records private. Vercel provides HTTPS for its assigned domain. For a custom domain verify ownership, use the DNS records in the Vercel dashboard and confirm TLS before setting SITE_ORIGIN and rebuilding. Roll back through Vercel's previous production deployment if needed.

POST /api/leads accepts same-origin JSON. Field limits are shared by the build and server. Five new applications per rolling-window bucket per network per hour; keyed network hashes expire on subsequent submissions. Duplicate keys and payloads reuse a record. Different payloads with the same key receive 409. Persistence precedes both notifications. Messages have distinct provider idempotency keys and persisted delivery flags. A provider failure retains the record, returns 503 and allows retry from the form. Monitor unsent flags in the restricted database and reconcile provider delivery logs before a manual resend, particularly after the provider's idempotency window. No PII is written to application logs. Reviewers update lead_status and notes in the database.

Use the customer's reference to find the record and verify the requester before fulfilling access or deletion requests. The owner must agree a retention period, configure scheduled cleanup of records, backups and email history with their providers, and update the notice before opening intake. Define a real operational contact and legal terms for the chosen jurisdiction. No fabricated countdown, booking link or SLA is used.

## Evidence and measurement

Keep private raw evidence, names pending permission and PII outside this public repository. Add only cleared case content to src/content.js. Case records use category, slug, clientDisplayName, challenge, diagnosis, scope[], approach[], outcomeText, evidenceType, disclaimer, publicationApproved, confidentialityApproved and optional evidenceVerified, metricPeriod, metricDefinition, metricValue, metricLabel. Numeric results require verified metrics with a period and definition. Projections do not qualify. Testimonials require consentApproved and publicationApproved, exact quote and attribution. The seven anonymized workstreams in src/project-briefs.js summarize the supplied project records. Their generated editorial images illustrate subject matter and are not client evidence. An approved case with the same slug replaces its anonymized summary.

No GA4 or Meta script is installed. An approved consent manager can set window.growthAnalyticsConsent=true before the page script, and an owner-approved collector can listen for growth:analytics events. Supported events are page_view, hero_cta_click, roadmap_view, offer_cta_click, form_start, form_submit_attempt, form_submit_success and form_submit_error. No lead values or IDs are sent in events. Consent gates session-scoped first-touch attribution. Do not enable a booking or Purchase event here without a corresponding real business event.
